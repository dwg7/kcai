# 配り方の設計：閉じた環境でも読める形

`PRINCIPLES.md` の原則 12（閉じた環境でも読める形で配る）の設計案である。**実装は未着手で、採否は hfu が決める。** 選択肢と利点・欠点を示す。

## 前提

- 読む人の環境は、さまざまである。ネットワークに届かない端末、外部のリポジトリを読めない AI、添付できるファイルの種類が限られる環境がありうる。kcai は、そうした環境の事情を前提にしない。**ファイルを一つ受け取れれば読める**ことを目標にする。
- 読む人が知りたいのは、「どの踏み跡を、どこまで確かめたか」である（原則 5）。配布物は、内容と同じ重みで、この情報を示す。
- 配布物にも、原則 7（公開できるものだけ）、原則 13（宣伝や、推薦を受けたような表示をしない）が及ぶ。

## 1. ひとまとまりの形

実測の目安（最初のインスタンス、2026-10-21。踏み跡約 100 件）: 本文 UTF-8 で約 0.6 MB（約 29.5 万字）、zip にして約 0.28 MB、PDF（`scripts/build_pdf.py`）は約 5.4 MB。

| 形 | 利点 | 欠点 |
|---|---|---|
| A. 単一の Markdown ファイル（全踏み跡を連結し、先頭に目次を付ける） | 1 ファイルで足りる。AI にそのまま添付・貼付できる。外部通信が要らない。テキストなので差分を取れる | 大きい。約 29.5 万字は、文脈長の短い AI では全体を一度に入れられない。一部だけを選びにくい |
| B. zip（`knowledge/*.md`、`INDEX.md`、`MANIFEST.json`、ライセンス） | 構造が保たれる。必要な踏み跡だけを選べる。圧縮される | zip を受け付けない環境がある。展開が要る。AI に直接渡せない |
| C. A と B の両方 | 環境に合わせて選べる | 作る手間と、食い違いの恐れ（同じ元から機械的に作れば避けられる） |
| D. PDF | 人が読むのに向く。既に作れる | AI には不向き。サイズが大きい。差分が取れない |
| E. 主題別・核だけの小さな束 | 短い文脈の AI に向く | 分け方の判断が要る。目次との整合を保つ手間 |

**推薦**: C（A と B を同じ元から機械的に作る）。D は人向けの任意の追加。E は、A が大きくなりすぎたときに検討する。

## 2. 版の付け方

| 方式 | 利点 | 欠点 |
|---|---|---|
| セマンティックバージョニング（1.2.0 など） | 慣れた人が多い | 知識では「互換性を壊す変更」が定義しにくい |
| 日付版（例: `2026.10.21`、同日に複数なら `2026.10.21.2`） | 知識は日付で語られる（`as_of`、確認日）。いつの束かが直ちに分かる | 変更の大きさは分からない |
| git のタグとコミットだけ | 追加の決めごとが要らない | git を使えない読み手には意味がない |

**推薦**: 日付版を主にし、コミットの識別子を併記する。束の中に `MANIFEST.json`（版、コミット、作成日時、踏み跡の件数、`status` ごとの件数、各ファイルの SHA-256）を入れる。ファイルの完全性は、`sha256sum -c`（ネットワーク不要）で確かめられる。

## 3. リリースの作り方

| 方式 | 利点 | 欠点 |
|---|---|---|
| a. 手動で GitHub Releases に添付 | 仕組みが要らない | 作り忘れ、作り間違い、A と B の食い違い |
| b. タグを付けると GitHub Actions が検査し、束を作って Releases に添付 | 再現できる。検査（`validate_knowledge.py`）を通ったものだけが配られる。チェックサムを自動で付けられる | ワークフローの保守が要る |
| c. main へのマージごとに Actions のアーティファクトとして保存 | 常に最新を取れる | アーティファクトは期限で消える。版の意味が弱い |

**推薦**: b。束の作成は、標準ライブラリだけで動く `scripts/build_bundle.py`（既存のスクリプトと同じ流儀）で行い、手元でも同じ束を作れるようにする。

**留意**: 公開前の確認が済んでいないインスタンスは、非公開のまま運用されることがある。その場合、Releases も共同作業者にしか見えない。束は、管理責任者が、チェックサムを添えて手渡しできる形にしておく。

## 4. 目次（確かめた度合いの一覧）

束の先頭に置く。読む人が、全体の信頼度を一目で判断できるようにする。

1. **要約**: 版、作成日、踏み跡の件数、`status` ごとの件数（`draft` / `reviewed` / `stable`）、`reviewed_by` が空でない件数、最も古い出典確認日、`unsaid`（語り得ぬこと）を持つ件数。
2. **読み方**: `status` の意味、`as_of` と `freshness` の意味、`docs/responsible-use.md` の要点（`draft` はそのまま業務の根拠にしない）。
3. **一覧表**: `id`、題名、`status`、確認者の有無、`as_of`、`freshness`、`unsaid` の有無、主な出典の確認日。
4. **本文**: 目次の順に、踏み跡を並べる（A の場合）。

`scripts/build_index.py` が既に持つ情報（`status`、`as_of`、`freshness`、`cites`、`unsaid`）から、機械的に作れる。

## 5. 外部への通信なしに読めること

- 束は自己完結にする。外部の画像、スクリプト、外部への埋め込みを含めない。
- 踏み跡どうしのリンクは、束の中の見出し（A）または相対パス（B）にする。
- 出典の URL は、**参照の記録**として書く（確認日と版を併記）。読むときに開けなくてもよい。要約が、出典なしでも読める形になっている。
- 文字コードは UTF-8、改行は LF。リンク切れは束の作成時に検査する。
- AI に渡すときの指示文の例を、目次の「読み方」に添える（例: 「以下は版 2026.10.21 の踏み跡の束である。`status` が `draft` のものは人が確認していない。回答では、根拠にした踏み跡の `id` と `status` を示すこと。」）。

## 6. 配布物に含めないもの

- 宣伝文、勧誘、特定の組織の推薦や公式な取り組みと読める表示（原則 13）。
- 公開できない情報（原則 7）。
- 利用者の AI や環境に関する指示（特定の AI 製品に依存する書き方。原則 1）。

## 7. 実装の道筋（提案）

1. `scripts/build_bundle.py`（標準ライブラリのみ）: 目次付きの単一 Markdown、zip、`MANIFEST.json`、チェックサムを作る。
2. `.github/workflows/release.yml`（ひな形に同梱）: 版タグで、検査 → 束の作成 → Releases への添付。
3. 最初のインスタンスで試し、実際に閉じた環境の読み手から、使い勝手を聞く。
